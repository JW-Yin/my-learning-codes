# 简述 DB、DBMS、DBA、DBS

## 1. DB（Database）——数据库
**含义**：长期存储在计算机内、**有组织、可共享、统一管理**的数据集合。

## 2. DBMS（Database Management System）——数据库管理系统
**含义**：位于用户与操作系统之间的一层**数据管理软件**，
是数据库系统的**核心**，负责对数据库进行定义、操纵、控制和维护。

## 3. DBA（Database Administrator）——数据库管理员
**含义**：负责**全面管理和控制数据库系统**的专业人员。
职责：模式定义、存储结构定义、权限管理、备份恢复、性能优化等。

## 4. DBS（Database System）——数据库系统
**含义**：指引入数据库后的整个计算机系统，
由 **硬件 + DB + DBMS + 应用程序 + DBA/用户** 组成。

# DBMS 核心功能

DBMS 核心功能：**数据定义、数据操纵、运行控制、存储管理、备份恢复**。
数据库管理系统（DBMS）的**核心功能**主要有以下 5 类：

1. **数据定义功能（DDL）**
   定义数据库的**模式、外模式、内模式**，以及约束、索引等。

2. **数据操纵功能（DML）**
   实现对数据的**查询、插入、删除、修改**。

3. **数据库运行控制（事务与并发）**
   - 事务管理（ACID）
   - 并发控制
   - 完整性检查
   - 安全性与权限控制

4. **数据组织、存储与管理**
   负责数据在物理存储上的组织、存取与优化。

5. **数据库维护功能**
   - 备份与恢复
   - 数据导入/导出
   - 性能监控与优化

# 事务 & ACID特性

## 1. 事务的定义
**事务**是用户定义的一个**数据库操作序列**，这些操作**要么全做，要么全不做**，是一个不可分割的逻辑工作单位。
## 2. ACID 四大特性
1. **原子性（Atomicity）**
   事务是不可分割的最小单位，操作**要么全部执行，要么全部不执行**。

2. **一致性（Consistency）**
   事务执行前后，数据库的**完整性约束不变**，从一个一致状态变到另一个一致状态。

3. **隔离性（Isolation）**
   多个事务并发执行时，相互**不能干扰**，感觉不到其他事务存在。

4. **持久性（Durability）**
   一个事务一旦**提交**，对数据库中数据的修改是**永久性**的，后续故障不影响该结果。

---
# 事务的ACID特性（简述+作用）

ACID保证数据库在**并发访问和系统故障**下，依然**正确、可靠、一致、安全**。
## 1. 原子性（Atomicity）
事务是**不可分割的最小执行单位**，要么全部执行成功，要么全部不执行，不允许部分执行。

**作用：**
- **故障恢复**：保证系统崩溃后，未完成事务全部回滚，不会出现“做了一半”的不一致状态。
- **并发控制**：避免事务执行到一半被其他事务看到，保证操作完整性。
## 2. 一致性（Consistency）
事务执行前后，数据库的**完整性约束不被破坏**，数据始终保持合法、正确状态。

**作用：**
- **故障恢复**：崩溃恢复后数据库仍保持一致，不会出现违反约束的数据。
- **并发控制**：多个事务并发执行后，结果与串行执行一致，保证数据逻辑正确。
## 3. 隔离性（Isolation）
多个事务**并发执行时互不干扰**，一个事务的中间结果对其他事务不可见。

**作用：**
- **并发控制**：通过隔离级别（读未提交、读已提交、可重复读、串行化）解决脏读、不可重复读、幻读问题。
- **故障恢复**：保证故障恢复时不会读取到其他事务未提交的脏数据。
## 4. 持久性（Durability）
事务一旦**提交成功**，会因系统对数据库的修改**永久保存**，不故障丢失。

**作用：**
- **故障恢复**：提交后的数据必须持久化到磁盘，崩溃重启后依然存在。
- **并发控制**：保证提交结果不会被回滚或覆盖，确保最终结果可靠。

# 数据库隔离级别 & 解决的问题

- 级别从低到高：**读未提交 → 读已提交 → 可重复读 → 串行化**
- 问题：**脏读 → 不可重复读 → 幻读**
- 规律：**级别越高，解决问题越多，并发性能越低**

## 一、四个标准隔离级别（从低到高）
1. **读未提交（Read Uncommitted）**
2. **读已提交（Read Committed）**
3. **可重复读（Repeatable Read）**
4. **串行化（Serializable）**
## 二、三种并发问题
1. **脏读**：读到了**其他事务未提交**的数据（可能回滚）。
2. **不可重复读**：同一事务内，**同一行数据**多次读取结果不一样。
3. **幻读**：同一事务内，**查询结果的行数**不一样（像出现/消失了幻影行）。

## 三、隔离级别与问题对应表

| 隔离级别               | 脏读   | 不可重复读 | 幻读   |
| ------------------ | ---- | ----- | ---- |
| 读未提交               | ❌ 允许 | ❌ 允许  | ❌ 允许 |
| **读已提交（Oracle默认）** | ✅ 解决 | ❌ 允许  | ❌ 允许 |
| **可重复读（MySQL默认）**  | ✅ 解决 | ✅ 解决  | ❌ 允许 |
| 串行化                | ✅ 解决 | ✅ 解决  | ✅ 解决 |

# 三种故障 & 恢复方法

- **事务故障**：UNDO 撤销
- **系统故障**：UNDO 未提交 + REDO 已提交
- **介质故障**：重装备份 + REDO 后续日志
## 1. 事务故障
- **定义**：事务执行过程中出错（如运算错误、死锁、违反约束）。
- **恢复方法**：
  **撤销（UNDO）该事务**
  对事务已修改的数据做**反向操作**，保证该事务**全部不执行**。
## 2. 系统故障（停电、宕机）
- **定义**：系统崩溃，内存数据丢失，磁盘数据还在。
- **恢复方法**：
  1. **UNDO** 所有**未提交**的事务
  2. **REDO** 所有**已提交但未写入磁盘**的事务
## 3. 介质故障（硬盘损坏、数据丢失）
- **定义**：外存物理损坏，数据库数据丢失。
- **恢复方法**：
  1. 重装系统，修复磁盘
  2. **重装最近的数据库备份**
  3. 用日志文件**REDO** 备份后的所有已提交事务

# 基础词汇

1. **码（键，Key，超码，Super Key）**
   能**唯一标识**一个元组（一行记录）的**属性或属性集合**，**可以包含多余属性**，不一定最小。

2. **候选码（候选键，Candidate Key）**
   **最小的超码**：能唯一标识元组，且**去掉任何一个属性就不再唯一**。
   一个关系可以有多个候选码。

3. **主键（主码，Primary Key）**
   从**候选码中选定一个**，作为该关系的**主要唯一标识**。
   一个关系只有一个主键，要求**非空、唯一**。

4. **主属性（Prime Attribute）**
   **包含在任意一个候选码中的属性**。

5. **非主属性（Non-Prime Attribute）**
   **不包含在任何候选码中的属性**。

6. **全码（All-Key）**
   整个关系的**所有属性共同组成唯一的候选码**，此时**所有属性都是主属性**。

7. **外键（外码，Foreign Key）**
   一个关系中的属性，它是**另一个关系的主键**，用于**建立表间联系**，保证参照完整性。

# 函数依赖 & 部分/传递/多值依赖

- **函数依赖**：X 定，Y 唯一。
- **部分依赖**：主键是组合键，Y 只依赖其中一部分。
- **传递依赖**：X→Y，Y→Z ⇒ X 传递决定 Z。
- **多值依赖**：X 对应一组 Y，互相独立，产生冗余。
## 1. 函数依赖（FD）
设 X、Y 是关系的属性集。
如果**对于 X 的每一个值，Y 都有唯一确定的值与之对应**，就称 **Y 函数依赖于 X**，记作：
**X → Y**

- X：决定因素
- Y：被决定因素
## 2. 部分函数依赖
- 前提：X 是**组合主键**（由多个属性组成）
- 定义：Y 只依赖于 X 中的**一部分属性**，而不是整个 X。
- 记作：**X → Y（部分）**

> 例：(学号, 课程号) → 姓名
> 姓名**只依赖学号**，不依赖课程号 → 部分函数依赖。
## 3. 传递函数依赖
- 条件：
  1. X → Y
  2. Y → Z
  3. Y 不能推出 X
- 则 **Z 传递函数依赖于 X**。

> 例：学号 → 系号，系号 → 系主任
> 系主任**传递依赖于学号**。
## 4. 多值依赖（MVD）
- 定义：在关系中，**X 的一个值对应一组 Y 值**，且这组值与其他属性 Z 无关。
- 记作：**X →→ Y**
- 特点：会产生**大量冗余**，是 4NF 要消除的问题。

# 数据库范式判定标准

- 1NF：**属性不可分**
- 2NF：**消除部分依赖**
- 3NF：**消除传递依赖**
- BCNF：**决定因素必含码**
- 4NF：**消除多值依赖**
## 1. 1NF（第一范式）
**判定：属性不可再分，无复合属性。**
- 每一列都是**原子值**。
- 只要有可拆分的列，就不满足1NF。
## 2. 2NF（第二范式）
**判定：满足1NF，且消除 部分函数依赖。**
- 所有**非主属性**都**完全函数依赖**于主键。
- 只要有非主属性只依赖主键的**一部分**，就不是2NF。
## 3. 3NF（第三范式）
**判定：满足2NF，且消除 传递函数依赖。**
- 非主属性**不传递依赖**于主键。
- 只要存在：主键→A→B，就不是3NF。
## 4. BCNF（BC范式）
**判定：满足3NF，且所有决定因素都包含码。**
- 只要有一个 **X→Y**，而 **X 不是超码**，就不是BCNF。
## 5. 4NF（第四范式）
**判定：满足BCNF，且消除 非平凡多值依赖。**
- 不允许 **X→→Y** 这种多值依赖存在。

# 最简单判断顺序（考场步骤）
1. 找**主键/码**
2. 看是否**原子**（是） → 1NF
3. 看是否**部分依赖**（否） → 2NF
4. 看是否**传递依赖** （否）→ 3NF
5. 看**所有左边是否都是码**（是） → BCNF
6. 看**有没有多值依赖** （否）→ 4NF

# 数据库的完整性约束

数据库完整性约束是**为了保证数据库中数据的正确性、一致性和合法性**，防止无效、错误数据进入数据库而设置的一系列规则。数据库完整性约束从**实体、引用、字段、业务**多个层面保证数据**准确、一致、可靠、无错误**。

主要分为以下 **5类高频考点**：

## 1. 实体完整性
- 规则：**主键（PRIMARY KEY）的值不能为NULL，且必须唯一**。
- 作用：保证每一行数据都能唯一标识，不存在重复或无法区分的实体。

## 2. 参照完整性（引用完整性）
- 规则：**外键的值要么为空，要么必须是被参照表主键中已存在的值**。
- 作用：保证表与表之间关联正确，防止出现无效引用。

## 3. 用户定义完整性
- 规则：根据业务需求自定义的约束，如 **NOT NULL、UNIQUE、CHECK、DEFAULT** 等。
- 作用：满足具体应用的数据合法性要求。

## 4. 域完整性
- 规则：字段的值必须符合**数据类型、长度、格式、范围**等定义。
- 作用：保证单个字段数据有效。

## 5. 触发器（常被问到）
- 作用：通过自定义程序自动检查、维护更复杂的业务完整性。

# 关系模型的参照完整性规则

参照完整性是**关系数据库中表与表之间数据引用的约束规则**，核心是**保证外键与主键之间引用的有效性**。**外键的值要么为空，要么必须是被参照表主键中已存在的值，不允许引用不存在的实体。**

**规则内容：**
1. 若属性（或属性组）**F** 是关系 **R** 的**外键**，参照关系 **S** 的**主键** **K**；
2. 则 **F** 上的每个取值必须满足：
   - 要么**等于 S 中某个主键值**（引用存在的实体），
   - 要么**全部为空值（NULL）**。

# 登记日志文件必须遵循的两大原则

**先写日志，再写库；按时间顺序写日志。**

1. **先写日志文件，后写数据库（先写日志原则）**
   只有把对数据的修改操作**先写入日志文件**，才允许真正修改数据库中的数据。

2. **严格按事务执行的时间次序登记日志**
   多个事务并发执行时，日志的写入顺序必须和事务**实际执行的时间顺序一致**，不能乱序。

# 数据库三层模式 + 优点

数据库三层模式是**外模式、模式、内模式**，通过两层映像实现**数据逻辑独立性和物理独立性**，简化使用、利于共享与安全。

## 一、三层模式（从外到内）

1. **外模式（子模式 / 用户模式）**
   面向单个用户/应用，是**局部数据的逻辑结构**，一个数据库可以有多个外模式。

2. **模式（概念模式 / 逻辑模式）**
   整个数据库**全局统一的逻辑结构**，只有一个。

3. **内模式（存储模式）**
   数据**物理存储结构与存储方式**，对应磁盘文件、索引、存储路径等。
## 二、两层映像（保证独立性）

- 外模式/模式映像：保证**逻辑独立性**
- 模式/内模式映像：保证**物理独立性**
## 三、三层模式结构的好处

1. **数据逻辑独立性**
   模式（全局逻辑）改变时，只需修改外模式/模式映像，**应用程序不用改**。

2. **数据物理独立性**
   内模式（存储）改变时，只需修改模式/内模式映像，**逻辑结构与程序不变**。

3. **简化用户使用**
   用户只看外模式，不用关心底层存储与全局结构。

4. **利于数据共享与安全**
   不同用户用不同外模式，便于权限控制与数据共享。

# 冲突可串行化 与 可串行化

- 如果多个事务并发执行，最终得到的结果与某一顺序调度的执行结果一致，就叫做可串行化（不管过程，结果正确即可）。
- 如果多个事务并发执行，最终得到的结果与某一顺序调度的执行结果一致，并且可以通过调换非冲突操作的顺序，使得操作序列和某一顺序执行的顺序完全一致，就叫做冲突可串行化。

> 冲突操作：两个操作，**来自不同事务、操作同一个数据、至少一个是写**，这两个操作就是 **冲突操作**。

---
# 并发调度正确性标准 + 如何保证

- **正确性标准**：**可串行化**，即并发执行结果等价于某一串行执行结果。
- **保证方法**：主要通过**两段锁协议（2PL）**、**封锁机制**、冲突可串行化判断，保证调度可串行化。

## 一、并发调度正确性的标准

**可串行化（Serializable）** 是并发调度正确性的唯一标准。

含义：
多个事务**并发执行**的结果，与这些事务**按某一次序串行执行**的结果相同。
即：**并发调度等价于某个串行调度**。

## 二、如何保证并发调度正确

1. **冲突可串行化**
   通过判断冲突操作（读写、写读、写写）的顺序是否等价于串行顺序，是最常用的可串行化判定。

2. **两段锁协议（2PL）**
   所有事务必须分两个阶段对数据项加锁、解锁：
   - **扩展阶段**：只能加锁，不能解锁
   - **收缩阶段**：只能解锁，不能加锁
   遵循两段锁协议，**一定能产生可串行化调度**。

3. **封锁机制**
   用**排他锁（X锁）、共享锁（S锁）** 控制并发访问，避免数据不一致。

4. **MVCC（多版本并发控制）**
   通过数据多版本实现读写不冲突，保证可串行化或高隔离级别。

---
# 两段锁协议

事务必须**先一次性把所有锁都加上，再统一解锁**，不允许边加锁边解锁。遵循两段锁协议，**一定能产生可串行化调度**，保证并发执行正确。

**两段锁协议（2PL）** 是保证并发调度**可串行化**的封锁协议，规定所有事务对数据的加锁、解锁必须分为两个阶段：

1. **扩展阶段（加锁阶段）**
   事务可以**不断申请并获得**所有需要的数据锁，但**不能释放任何锁**。

2. **收缩阶段（解锁阶段）**
   事务可以**不断释放**已经持有的锁，但**不能再申请任何新锁**。

# 视图与基本表的核心区别

视图是**虚表**，不存数据；既能**隐藏数据、控制访问**提高安全性，又能**屏蔽表结构变化**，保障逻辑独立性。

- **基本表**：实际存储数据的**实表**，是数据库的原始数据。
- **视图**：**虚表**，本身**不存储数据**，只存储查询定义，使用时动态从基本表导出结果。

核心区别一句话：
**基本表存数据，视图不存数据，只是查询定义。**

---
# 视图在安全性的作用

- 屏蔽敏感字段与无关数据，**只向用户开放其权限范围内的数据**。
- 用户只能看到视图内容，无法访问底层完整基本表，**防止越权查看/修改**。
- 简化权限管理，实现**按需可见、最小权限**。

---
# 视图在逻辑独立性的作用

- 当**基本表结构修改**（增删字段、改名、分表）时，可通过**修改视图定义**保持视图结构不变。
- 上层应用程序面向视图开发，**无需修改代码**，屏蔽底层结构变化，保证**逻辑独立性**。

# 什么是聚簇（聚簇索引 / 簇）

**聚簇就是让数据在磁盘上按聚簇码物理有序、集中存放，从而大幅提速。**

**聚簇**是指：将**聚簇码值相同/相近的数据记录，在物理磁盘上连续集中存放**的存储组织方式。
## 核心特点（3句背完）
1. 数据的**物理存储顺序**与**聚簇码的逻辑顺序一致**。
2. 数据与索引**存在一起**，不是分开存放。
3. 一个表**只能有一个聚簇**（因为物理顺序只能一种）。
## 优点
- 按聚簇码**等值、范围查询、多表连接**极快
- 大幅**减少磁盘 I/O**，查询效率最高

# 多对多联系

**多对多联系（m:n）**：是实体之间的一种联系类型，表示**A实体中的一个实例，可以与B实体中的多个实例关联**；同时**B实体中的一个实例，也可以与A实体中的多个实例关联**。
### 经典例子（面试必说）
- **学生 ↔ 课程**：一个学生可选多门课，一门课可被多个学生选。
- **读者 ↔ 图书**：一个读者可借多本书，一本书可被多个读者借阅。
### 必考点（转化方法）
多对多联系**不能直接存为外键**，必须**拆成两个一对多**，中间加**关联表**。
- 关联表包含：双方实体的主键 + 联系自身属性。

# 什么是大数据

大数据是**海量、高速、多样、低价值密度、真实**的数据集合，需用分布式、并行计算等新技术处理，以挖掘价值。

大数据是指**无法在一定时间内用传统数据库软件进行抓取、管理、处理的数据集合**，它具有海量、高速、多样、低价值密度、真实性的特点，需要新处理模式才能具有更强的决策力、洞察发现力和流程优化能力。

## 核心特征（5V，面试必答）
1. **Volume（大量）**：数据规模巨大，TB→PB→EB级
2. **Velocity（高速）**：产生、传输、处理速度快，要求实时响应
3. **Variety（多样）**：数据类型多，结构化、半结构化、非结构化（文本、图片、音频、视频）
4. **Value（低价值密度）**：数据总量大，但有用信息少，需要挖掘
5. **Veracity（真实性）**：数据可信、准确、可靠

# 左外连接特点

**左表全出，右表匹配，不匹配为空。**

**左外连接（LEFT JOIN）**：以**左表为基准**，返回**左表所有记录**，并匹配右表中符合条件的记录；
右表无匹配时，右表字段用 **NULL** 填充。
### 核心特点（3句背完）
1. **左表数据全部保留**，不丢失任何一行
2. **右表只保留匹配成功**的行
3. **匹配不上的位置填 NULL**

# 触发器特点

**自动触发、事件驱动、与事务一体、可实现复杂完整性。**

触发器是用户定义在**基本表上**的一类**由事件自动触发执行**的特殊存储过程，不由用户直接调用。

### 核心特点（直接背）
1. **自动触发**：由 INSERT/UPDATE/DELETE 事件自动激发，无需手动调用。
2. **与触发事件绑定**：定义在表上，随表数据变动而执行。
3. **原子执行**：触发器与触发语句同属一个事务，要么都成功，要么都回滚。
4. **可多级触发**：一张表可定义多个触发器，也可触发其他表的触发器。
5. **强约束能力**：能实现比主键、外键、CHECK 更复杂的业务完整性与一致性。
6. **事后/事前控制**：可分为 BEFORE 与 AFTER 类型，用于校验、级联操作、日志记录。

# 数据库角色的定义

**角色是权限的打包集合，用于批量、统一、高效地管理用户权限。**

**数据库角色**是被命名的一组**相关权限的集合**，用于简化权限管理。
它是为了方便批量给多个用户统一分配、回收权限而创建的**权限容器**。

### 核心要点（直接背）
1. **一组权限的命名集合**：把增、删、改、查等权限打包成一个角色。
2. **简化授权**：给用户授权时，直接授予角色，不用逐条赋权。
3. **统一管理**：修改角色权限，所有拥有该角色的用户自动生效。
4. **方便回收**：回收角色即可收回一组权限，便于运维与安全控制。

# 并发带来的三个问题

- 脏读：读**未提交**
- 不可重复读：读**已修改**
- 幻读：读**增删后的行数变化**

多个事务并发执行时，若不加控制，会出现**脏读、不可重复读、幻读**，导致数据不一致。

1. **脏读**
一个事务读到了**另一个事务未提交的更新数据**，若对方回滚，该数据无效（脏数据）。

2. **不可重复读**
一个事务内**多次读取同一数据**，期间被其他事务修改并提交，导致**多次读取结果不一致**。

3. **幻读**
一个事务按同一条件**多次查询**，期间其他事务执行插入/删除并提交，导致结果集**突然多出或缺少行**（像幻觉）。

# 一、二、三级封锁协议

- 一级：**改加X锁到结束** → 防丢失
- 二级：**读加S锁读完放** → 防脏读
- 三级：**读加S锁到结束** → 防重复读

### 一级封锁协议
- 规则：事务**修改数据**时，必须加**排他锁（X锁）**，直到**事务结束**才释放。
- 解决：**丢失修改**。
- 不解决：脏读、不可重复读。

### 二级封锁协议
- 规则：在一级基础上，事务**读取数据**前加**共享锁（S锁）**，**读完立即释放**。
- 解决：丢失修改、**脏读**。
- 不解决：不可重复读。

### 三级封锁协议
- 规则：在一级基础上，事务**读取数据**前加**共享锁（S锁）**，直到**事务结束**才释放。
- 解决：丢失修改、脏读、**不可重复读**。

# 视图消解

**把对视图的查询，转换成对基本表的查询，这个过程叫视图消解。**

**视图消解**是指：数据库在执行对**视图**的查询时，将**视图的定义语句**与**用户查询语句**进行合并、等价转换，最终**解析成对基本表的直接查询**的过程。

### 核心要点（背这3句）
1. 视图是**虚表**，不存数据，不能直接查询。
2. 执行视图查询时，系统自动把**视图SQL + 用户查询SQL**合并。
3. 转换为对**基本表**的有效查询，这个转换过程就是**视图消解**。

# 事务故障、系统故障、介质故障恢复技术

- 事务故障：只 **UNDO**
- 系统故障：先 **UNDO** 再 **REDO**
- 介质故障：**备份+REDO**

### 1. 事务故障（事务内部出错、未提交）
- 恢复方法：**UNDO（撤销）**
- 步骤：反向扫描日志，对**未提交事务**撤销所有修改，恢复原值。

### 2. 系统故障（断电、宕机，内存丢、磁盘在）
- 恢复方法：**UNDO + REDO**
- 步骤：
  1. 先做 **UNDO**：撤销所有未提交事务
  2. 再做 **REDO**：重做所有已提交但未写入磁盘的事务

### 3. 介质故障（磁盘损坏，数据丢失）
- 恢复方法：**重装 + 备份 + REDO**
- 步骤：
  1. 重装数据库
  2. 装入**最近完整备份**
  3. 重做备份之后的所有已提交事务（REDO）

# 为什么索引能让查找变快？

索引是建立在表上的**有序快速查找结构**，将**全表扫描**转为**快速定位**，**大幅减少磁盘 I/O**，从而显著提升查询速度。

**核心原因一句话：索引把“逐行全盘扫描”变成了“快速定位查找”，大幅减少磁盘 I/O 次数。**

## 详细通俗版（面试直接口述）
1. **不加索引**
   要找某条数据，必须**从头到尾逐行扫描**整张表，数据越多越慢。

2. **加了索引**
   索引是**有序的查找结构**（如 B+ 树），相当于书的**目录**：
   - 先在目录里**快速定位页码**
   - 再直接跳到对应位置读取数据
   不用再从头翻到尾。

3. **根本提速原理**
   - 索引**有序、高度精简**，比原表小得多
   - 用**二分查找、树查找**代替全盘遍历
   - **最少的磁盘 I/O 次数**找到目标（磁盘 I/O 是最慢的）

# MySQL 与其他数据库的核心区别

MySQL 是**开源轻量、跨平台、易用性高**的关系型数据库，对比 Oracle/SQL Server 更轻量化、低成本，对比 PostgreSQL 更侧重互联网场景的高性能读写。
### 1. 与 Oracle 对比
- MySQL：开源免费，轻量级，中小型应用首选；默认存储引擎 InnoDB 支持事务/行锁，部署维护简单。
- Oracle：闭源收费，重量级，企业级核心系统用；功能全（分区、集群、高级安全），性能强但部署复杂、成本高。

### 2. 与 SQL Server 对比
- MySQL：跨平台（Linux/Windows），开源生态丰富，适合互联网分布式架构。
- SQL Server：微软出品，仅支持 Windows，与.NET 生态深度绑定，适合微软技术栈的企业内网系统。

### 3. 与 PostgreSQL 对比
- MySQL：易用性高，读写性能优，社区活跃，互联网场景（电商、社交）主流。
- PostgreSQL：更贴近标准 SQL，支持复杂数据类型（数组、JSON）、自定义函数，适合数据分析/科研场景。

# InnoDB 和 MyISAM 核心区别

InnoDB 支持**事务、行锁、外键**，适合高并发/强一致性场景；MyISAM 仅表锁、无事务，适合只读/低并发场景。

### 1. 事务支持（最核心）
- InnoDB：**支持事务（ACID）**，可回滚、提交，适合金融、电商等需数据一致性的场景。
- MyISAM：**不支持事务**，执行速度快，但数据出错无法回滚。

### 2. 锁机制
- InnoDB：**行级锁**，仅锁定修改的行，并发读写性能优。
- MyISAM：**表级锁**，修改数据时锁整张表，高并发下性能差。

### 3. 外键与崩溃恢复
- InnoDB：**支持外键约束**，崩溃后可自动恢复数据，数据完整性强。
- MyISAM：**不支持外键**，崩溃后易损坏，需手动修复。

### 4. 存储与索引
- InnoDB：聚簇索引结构，数据与索引存一起，需主键；支持全文索引（5.6+）。
- MyISAM：非聚簇索引，数据与索引分开存，无主键也能建；全文索引原生支持。

# 什么是检查点？有何作用

**检查点**是数据库系统周期性建立的**数据同步点**，用于将内存缓冲区中已修改的数据与日志，批量写入磁盘，并记录当前日志位置。

### 作用
1. **缩短故障恢复时间**，无需从头扫描全部日志
2. **减少内存数据丢失风险**，定时刷盘
3. **明确恢复边界**，只需处理检查点之后的事务

# 意向锁

**先在表上打个“意向”标记，快速判断能不能锁全表。**

**意向锁**是加在**表层级**的一种**提前声明锁**，事务在给某行加锁前，先对整张表加意向锁，用来快速判断“整张表能不能加锁”。

### 核心作用
- 避免“想锁全表，却要逐行检查是否被锁”，**提升加表锁效率**
- 协调**表锁与行锁**，保证并发安全

# 可串行性调度

**可串行性调度**是指：多个并发事务的调度执行结果，与这些事务**按某一次序串行执行**的结果完全一致，它是判断并发调度**正确、保证数据一致**的最高标准。

# 数据库优化原则

一句话：**先优结构与索引，再优SQL与事务，最后扩架构。**

1. **结构优化**：设计遵循三范式，适度反范式，合理分库分表。
2. **索引优化**：为高频查询建索引，避免冗余索引，最左前缀匹配。
3. **SQL优化**：避免全表扫描，减少子查询，慎用*，合理连接。
4. **事务优化**：缩短事务时长，降低锁等待，减少死锁。
5. **参数优化**：调整缓存、连接数、I/O等参数提升效率。
6. **硬件与架构**：升级配置、读写分离、主从复制。

# 数据库设计步骤

1. **需求分析**：明确数据、功能、约束，产出数据字典与需求文档。
2. **概念结构设计**：抽象实体与联系，绘制**E-R图**。
3. **逻辑结构设计**：将E-R图转为关系表，设计**键与范式**优化。
4. **物理结构设计**：选定库、存储引擎、索引、分区等。
5. **数据库实施**：建库建表、编写约束与视图、导入数据。
6. **数据库运行与维护**：监控、备份、优化、扩容。

# 概念模型的特点（E-R模型）

1. **独立于硬件与软件**，不依赖具体数据库与计算机。
2. **语义表达清晰**，能直观反映实体、属性与联系。
3. **易于理解交流**，方便用户与设计人员沟通。
4. **易于转换**，可方便转为逻辑模型（关系表）。
5. **面向现实世界**，真实反映业务需求。
