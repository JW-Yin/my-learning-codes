# 超清晰 Ceph 全组件梳理（含英文全称、作用、依赖、必装/可选）
## 一、核心常驻进程（**所有Ceph集群必装、必运行**）
### 1. MON = Monitor（监视器）
- 核心定位：**集群大脑 & 仲裁中心**
- 核心作用：
  1. 保存集群全局配置、节点信息、权限密钥
  2. 维持 **Quorum（法定票数）**，防止集群脑裂
  3. 统一管控集群状态、故障判定
- 部署特点：必须奇数部署（3/5/7 台），保证高可用

### 2. OSD = Object Storage Daemon（对象存储守护进程）
- 核心定位：**真正存数据的干活单元**
- 核心作用：
  1. 直接管理本地硬盘/SSD，承载所有数据读写
  2. 负责数据多副本、纠删码、数据自愈、磁盘心跳
  3. 接收CRUSH调度，完成数据分片存放
- 部署特点：**一块磁盘 对应 一个OSD进程**

### 3. MGR = Manager（集群管理器）
- 核心定位：**集群运维监控中枢**
- 核心作用：
  1. 采集集群性能指标、状态数据
  2. 提供可视化面板、告警、Prometheus监控对接
  3. 运行各类后台插件、负载调度辅助
- 部署特点：默认双节点高可用，新版Ceph强制依赖

---

## 二、可选业务进程（**按需部署，不用则不装**）
### 4. MDS = Metadata Server（元数据服务器）
- 专属依赖：**仅 CephFS 文件存储 需要**
- 核心作用：
  1. 管理文件系统元数据：目录、文件名、权限、时间、目录树
  2. 隔离文件元数据与真实数据，提升共享文件性能
- 无依赖场景：只用RBD、对象存储时，完全不需要MDS

### 5. RGW = RADOS Gateway（RADOS对象网关）
- 专属依赖：**对外提供 S3/Swift 对象存储 需要**
- 核心作用：
  1. 把底层RADOS原生对象，封装为标准S3协议
  2. 提供多租户、桶管理、跨域复制、静态托管等对象能力
- 无依赖场景：只用块存储、文件存储时，可不用RGW

---

## 三、三大对外存储服务（用户实际使用的能力）
无独立后台进程，**依赖上面组件运行**
1. **RBD = RADOS Block Device**
   - 类型：**块存储**
   - 依赖：仅基础三巨头（MON+OSD+MGR），无需额外组件
   - 用途：云主机硬盘、K8s数据库卷、虚拟机磁盘

2. **CephFS = Ceph File System**
   - 类型：**分布式文件存储**
   - 依赖：基础三巨头 + **MDS**
   - 用途：多机器共享目录、AI数据集、日志集群

3. **S3 对象存储**
   - 类型：**对象存储**
   - 依赖：基础三巨头 + **RGW**
   - 用途：图片、备份、AI数据湖、归档资料

---

## 四、底层核心底座（无进程，Ceph架构根本）
1. **RADOS**
   全称：Reliable Autonomous Distributed Object Storage
   作用：Ceph底层分布式对象集群，**所有块/文件/对象数据，最终都会拆成RADOS对象存入OSD**

2. **CRUSH 算法**
   作用：去中心化数据分片规则，决定数据存在哪台机器、哪块磁盘，自动扩容、故障迁移

3. **BlueStore**
   OSD 默认底层存储引擎，直接裸盘读写，高性能、高压缩、生产环境标配

---

## 五、部署&运维编排组件（管理工具，二选一）
1. **Cephadm**
   场景：物理机、虚拟机、传统私有云
   作用：容器化部署Ceph集群、一键扩容、升级、故障自愈

2. **Rook**
   场景：Kubernetes 云原生环境
   作用：K8s算子形式，原生管理Ceph全生命周期

---

# 终极极简总结（背诵版）
1. **必装三核心**
MON(仲裁) + OSD(存数据) + MGR(监控管理)
2. **按需二组件**
MDS(文件专用) + RGW(对象S3专用)
3. **三类业务能力**
RBD块（自带）、CephFS文件（要MDS）、S3对象（要RGW）
4. **底层根基**
RADOS + CRUSH + BlueStore
5. **运维工具**
物理机用Cephadm，K8s用Rook
