在云原生安全/DevSecOps领域，大佬面对“Linux云服务器问题及时告警”的需求，**绝不会用“脚本内嵌邮件逻辑”这种零散方式**，而是构建一套「**全维度可观测 + 标准化告警 + 安全合规通知 + 自愈优先**」的体系——核心是“让机器自动发现问题、优先自愈、自愈失败再精准告警”，而非靠手写脚本的“单点通知”。

以下是她的完整实践思路（从架构选型到落地细节，适配个人Linux云服务器的轻量版，兼顾DevSecOps核心原则）：

### 一、核心架构选型（轻量但符合云原生规范）
大佬会选择「Prometheus生态 + 轻量日志组件 + 标准化告警分发」，工具栈极简且可扩展，适配个人服务器：
| 组件                | 核心作用                                                                 |
|---------------------|--------------------------------------------------------------------------|
| Node Exporter       | 监控服务器基础设施（CPU/内存/磁盘/网络/进程/文件系统），暴露Prometheus指标 |
| Process Exporter    | 监控自定义脚本/应用的进程状态（是否运行、退出码、执行时长、资源占用）     |
| Blackbox Exporter   | 监控外部依赖（如脚本访问的网站、自己的应用端口、数据库连接）是否可达       |
| Prometheus          | 统一采集所有指标，配置告警规则（“什么条件算问题”）                       |
| Alertmanager        | 统一管理告警（去重/分组/抑制），分发到邮件/钉钉/微信等渠道               |
| Fluent Bit + Loki   | 收集所有组件/脚本的结构化日志（便于审计、追溯问题根因）                   |
| Systemd             | 托管脚本/应用（进程挂了自动重启，实现基础自愈）                          |

### 二、落地步骤（从0到1搭建，符合DevSecOps原则）
#### 步骤1：基础设施监控（先兜底服务器层面的问题）
大佬首先会监控服务器本身，避免“脚本没告警，但服务器宕机了”的情况：
1. **部署Node Exporter**（Docker/二进制均可，个人推荐Docker，无需配置系统依赖）：
   ```bash
   # 启动Node Exporter（暴露9100端口，仅本机可访问，保证安全）
   docker run -d \
     --name node-exporter \
     --net="host" \
     --pid="host" \
     -v "/:/host:ro,rslave" \
     --restart=always \
     prom/node-exporter:latest \
     --path.rootfs=/host \
     --web.listen-address=127.0.0.1:9100  # 仅本机访问，避免外网暴露
   ```
2. **验证指标**：访问 `http://127.0.0.1:9100/metrics`，能看到服务器CPU、内存、磁盘等指标，说明部署成功。

#### 步骤2：脚本/应用监控（覆盖业务层面的问题）
针对自己跑的脚本/应用，大佬不会写“if判断+发邮件”，而是用标准化方式监控：
1. **用Process Exporter监控脚本进程**：
   - 配置Process Exporter（`process-exporter.yml`），指定要监控的脚本（比如`remind_me.py`）：
     ```yaml
     process_names:
       - name: "{{.Matches}}"
         cmdline:
           - "python3.*remind_me.py"  # 匹配脚本进程
     ```
   - 启动Process Exporter：
     ```bash
     docker run -d \
       --name process-exporter \
       --net="host" \
       --pid="host" \
       -v "$PWD/process-exporter.yml:/config.yml" \
       --restart=always \
       ncabatoff/process-exporter:latest \
       -config.path /config.yml \
       -web.listen-address=127.0.0.1:9256
     ```
2. **用Systemd托管脚本（基础自愈）**：
   大佬会把脚本注册为Systemd服务，进程挂了自动重启（自愈优先，减少告警）：
   - 创建服务文件 `/etc/systemd/system/monitor-web.service`：
     ```ini
     [Unit]
     Description=Web Monitor Script
     After=network.target

     [Service]
     User=jw-yin  # 非root用户运行，最小权限
     WorkingDirectory=/home/jw-yin/00-my_scripts/monitor_web_page
     ExecStart=/usr/bin/python3 /home/jw-yin/00-my_scripts/monitor_web_page/remind_me.py
     Restart=on-failure  # 进程失败自动重启
     RestartSec=30s  # 重启间隔30秒
     LogsDirectory=monitor-web  # 日志目录

     [Install]
     WantedBy=multi-user.target
     ```
   - 启动并开机自启：
     ```bash
     sudo systemctl daemon-reload
     sudo systemctl start monitor-web
     sudo systemctl enable monitor-web
     ```

#### 步骤3：部署Prometheus + 配置告警规则
Prometheus是“大脑”，负责采集指标、判断“是否出问题”：
1. **启动Prometheus**（配置文件`prometheus.yml`）：
   ```yaml
   global:
     scrape_interval: 15s  # 15秒采集一次指标（个人服务器足够）
     evaluation_interval: 15s

   scrape_configs:
     # 采集Node Exporter（服务器指标）
     - job_name: 'node'
       static_configs:
         - targets: ['127.0.0.1:9100']
     # 采集Process Exporter（脚本进程指标）
     - job_name: 'process'
       static_configs:
         - targets: ['127.0.0.1:9256']

   # 告警规则文件
   rule_files:
     - "alert-rules.yml"

   # 对接Alertmanager
   alerting:
     alertmanagers:
       - static_configs:
           - targets: ['127.0.0.1:9093']
   ```
2. **配置告警规则**（`alert-rules.yml`，定义“什么情况算问题”）：
   ```yaml
   groups:
     - name: server_alerts  # 服务器层面告警
       rules:
         # 磁盘使用率>85%告警
         - alert: HighDiskUsage
           expr: 100 - (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"} * 100) > 85
           for: 5m  # 持续5分钟才告警，避免抖动
           labels:
             severity: warning
           annotations:
             summary: "服务器磁盘使用率过高"
             description: "磁盘/使用率{{ $value }}%，已超过85%阈值"

         # CPU使用率>90%告警
         - alert: HighCPUUsage
           expr: 100 - (avg by (instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90
           for: 3m
           labels:
             severity: warning
           annotations:
             summary: "服务器CPU使用率过高"
             description: "CPU使用率{{ $value }}%，已超过90%阈值"

     - name: script_alerts  # 脚本层面告警
       rules:
         # 脚本进程消失（未运行）告警
         - alert: ScriptProcessDown
           expr: process_up{name="python3.*remind_me.py"} == 0
           for: 2m
           labels:
             severity: critical
           annotations:
             summary: "监控脚本进程已停止"
             description: "脚本remind_me.py进程消失，Systemd可能重启失败"

         # 脚本进程重启次数过多（说明脚本有异常）
         - alert: ScriptRestartTooMuch
           expr: increase(process_restart_count{name="python3.*remind_me.py"}[1h]) > 5
           for: 10m
           labels:
             severity: warning
           annotations:
             summary: "监控脚本重启次数过多"
             description: "1小时内脚本重启{{ $value }}次，可能存在逻辑错误"
   ```
3. **启动Prometheus**：
   ```bash
   docker run -d \
     --name prometheus \
     --net="host" \
     -v "$PWD/prometheus.yml:/etc/prometheus/prometheus.yml" \
     -v "$PWD/alert-rules.yml:/etc/prometheus/alert-rules.yml" \
     --restart=always \
     prom/prometheus:latest \
     --config.file=/etc/prometheus/prometheus.yml \
     --web.listen-address=127.0.0.1:9090  # 仅本机访问
   ```

#### 步骤4：部署Alertmanager（标准化告警分发）
Alertmanager负责“怎么通知”，大佬会配置**多渠道兜底**（即时渠道+邮件），且保证凭证安全：
1. **配置Alertmanager**（`alertmanager.yml`，敏感信息用环境变量，不硬编码）：
   ```yaml
   global:
     smtp_smarthost: 'smtp.qq.com:587'
     smtp_from: '{{ env "SMTP_FROM" }}'  # 从环境变量读发件人
     smtp_auth_username: '{{ env "SMTP_USER" }}'
     smtp_auth_password: '{{ env "SMTP_PASS" }}'  # 邮箱授权码（环境变量）
     smtp_require_tls: true

   route:
     group_by: ['alertname']  # 按告警名称分组
     group_wait: 30s  # 等待30秒，聚合同类型告警
     group_interval: 5m  # 同一组告警间隔5分钟再发
     repeat_interval: 1h  # 重复告警间隔1小时（避免轰炸）
     receiver: 'multi-channel'  # 默认接收器

   receivers:
     - name: 'multi-channel'
       # 渠道1：邮件通知
       email_configs:
         - to: '926115191@qq.com'
           subject: '[告警] {{ .CommonAlertName }} - {{ .CommonAnnotations.summary }}'
           html: |
             <h3>告警详情</h3>
             <p>告警名称：{{ .CommonAlertName }}</p>
             <p>告警级别：{{ .CommonLabels.severity }}</p>
             <p>描述：{{ .CommonAnnotations.description }}</p>
             <p>触发时间：{{ .StartsAt.Format "2006-01-02 15:04:05" }}</p>
       # 渠道2：钉钉机器人（即时通知，优先于邮件）
       webhook_configs:
         - url: '{{ env "DINGTALK_WEBHOOK" }}'
           send_resolved: true  # 问题恢复也通知
   ```
2. **启动Alertmanager**（通过环境变量传入敏感信息，避免硬编码）：
   ```bash
   docker run -d \
     --name alertmanager \
     --net="host" \
     -v "$PWD/alertmanager.yml:/etc/alertmanager/alertmanager.yml" \
     -e SMTP_FROM="926115191@qq.com" \
     -e SMTP_USER="926115191@qq.com" \
     -e SMTP_PASS="你的邮箱授权码" \
     -e DINGTALK_WEBHOOK="你的钉钉机器人webhook" \
     --restart=always \
     prom/alertmanager:latest \
     --config.file=/etc/alertmanager/alertmanager.yml \
     --web.listen-address=127.0.0.1:9093
   ```

#### 步骤5：日志审计（DevSecOps合规要求）
大佬会收集所有组件/脚本的结构化日志，便于追溯问题根因：
- 用Fluent Bit收集日志（服务器日志、Docker容器日志、脚本日志），推到Loki（轻量日志存储），核心是“所有操作可审计”，比如：
  - 脚本执行失败时，能通过日志快速定位是“网络问题”还是“代码逻辑问题”；
  - 告警触发后，能追溯“问题发生前服务器/脚本的状态”。

### 三、核心DevSecOps原则体现（大佬和普通写法的本质区别）
1. **最小权限**：
   - 所有组件仅本机访问（绑定127.0.0.1），避免外网暴露；
   - 脚本/应用以非root用户运行；
   - 邮箱授权码、钉钉webhook等敏感信息通过环境变量传入，不硬编码。
2. **自愈优先，告警兜底**：
   - Systemd自动重启挂掉的脚本，减少不必要的告警；
   - 告警规则加“持续时间”（如CPU高持续3分钟），避免抖动告警。
3. **可观测+可审计**：
   - 指标（Prometheus）+ 日志（Loki）双维度监控，问题可追溯；
   - 所有告警/通知操作都有记录，符合合规要求。
4. **标准化+可扩展**：
   - 新增脚本/应用时，只需在Process Exporter加配置、Prometheus加告警规则，无需改通知逻辑；
   - 新增通知渠道（如微信、短信）时，只需在Alertmanager加配置，无需改业务代码。

### 总结
DevSecOps大佬处理“Linux服务器问题告警”的核心不是“选Python还是Shell发邮件”，而是：
1. **全维度可观测**：服务器+应用+脚本的指标/日志全覆盖，不遗漏任何问题；
2. **标准化告警**：用Prometheus/Alertmanager替代手写的通知逻辑，规则可配置、可审计；
3. **安全合规**：敏感信息托管、最小权限运行、操作可追溯；
4. **自愈优先**：能自动修复的问题绝不告警，告警只针对“需要人工介入的严重问题”。


大佬**不会像你这样做“每个脚本配一套 shell + crontab + ssmtp”的零散写法**，但也不会完全抛弃你的 Python 爬虫核心逻辑（签到、网页对比）——核心思路是：**让业务脚本只专注做“签到/网页对比”，把定时、监控、告警这些重复性工作交给标准化工具**，既保留你熟悉的爬虫逻辑，又摆脱手工脚本的繁琐和不稳定性。

|---------------------|---------------------------------------|-------------------------------------|

### 大佬的具体做法（适配你的两个脚本，分步拆解）
核心原则：**业务逻辑（签到/网页对比）和监控告警解耦**，你的 Python 爬虫只负责“干活”，其他事交给标准化工具。

#### 步骤 1：重构核心 Python 脚本（只保留爬虫逻辑，输出改为“指标文件”）
你的脚本不用大改，只需要把“输出文字”改为“写入 Prometheus 能识别的指标文件”（纯文本，几行代码），让脚本只专注做“签到/网页对比”，不碰告警、输出判断。

##### 示例 1：重构签到脚本（signin.py）
```python
import requests
from bs4 import BeautifulSoup
import time
import os

# 【保留你的核心爬虫逻辑】
def do_signin():
    # 你的登陆、签到代码（原样保留）
    session = requests.Session()
    # ... 你的登陆逻辑 ...
    response = session.get("https://xxx.com/signin")
    soup = BeautifulSoup(response.text, "html.parser")
    # 判断是否签到成功
    if "签到成功" in soup.text:
        return 1  # 1=成功
    else:
        return 0  # 0=失败

# 【新增：将结果写入指标文件】
def write_metrics(status):
    # 指标文件路径（Node Exporter 能读取的目录）
    metrics_dir = "/var/lib/node-exporter/textfile_collector"
    os.makedirs(metrics_dir, exist_ok=True)
    metrics_file = f"{metrics_dir}/signin.prom"
    
    # 标准化 Prometheus 指标格式
    timestamp = int(time.time())
    metrics = f"""# HELP signin_status 签到状态（1=成功，0=失败）
# TYPE signin_status gauge
signin_status {status}
# HELP signin_last_check_time 最后一次签到时间戳
# TYPE signin_last_check_time gauge
signin_last_check_time {timestamp}
"""
    # 写入文件（原子操作，避免文件损坏）
    with open(f"{metrics_file}.tmp", "w", encoding="utf-8") as f:
        f.write(metrics)
    os.rename(f"{metrics_file}.tmp", metrics_file)

if __name__ == "__main__":
    try:
        status = do_signin()
        write_metrics(status)
    except Exception as e:
        # 异常时标记为失败
        write_metrics(0)
        print(f"签到异常: {e}")  # 仅用于调试，不影响告警
```

##### 示例 2：重构网页监控脚本（web_check.py）
```python
import requests
import hashlib
import os
import time
from bs4 import BeautifulSoup

# 【保留你的核心对比逻辑】
def check_web_update():
    TARGET_URL = "https://www.guet.edu.cn/yjszs/2025/0905/c4230a141350/page.htm"
    CACHE_FILE = "/var/lib/web_check/cache.html"
    headers = {"User-Agent": "Mozilla/5.0 ..."}
    
    # 获取当前页面
    response = requests.get(TARGET_URL, headers=headers, timeout=10)
    response.encoding = response.apparent_encoding
    current_html = response.text
    
    # 对比缓存
    if os.path.exists(CACHE_FILE):
        with open(CACHE_FILE, "r", encoding="utf-8") as f:
            old_html = f.read()
        if hashlib.sha256(current_html.encode()).hexdigest() != hashlib.sha256(old_html.encode()).hexdigest():
            # 有更新，更新缓存
            with open(CACHE_FILE, "w", encoding="utf-8") as f:
                f.write(current_html)
            return 1  # 有更新
        else:
            return 0  # 无更新
    else:
        # 首次运行，保存缓存
        os.makedirs(os.path.dirname(CACHE_FILE), exist_ok=True)
        with open(CACHE_FILE, "w", encoding="utf-8") as f:
            f.write(current_html)
        return 0

# 【新增：写入指标文件】
def write_metrics(status):
    metrics_dir = "/var/lib/node-exporter/textfile_collector"
    os.makedirs(metrics_dir, exist_ok=True)
    metrics_file = f"{metrics_dir}/web_check.prom"
    
    timestamp = int(time.time())
    metrics = f"""# HELP web_update_status 网页更新状态（1=有更新，0=无更新）
# TYPE web_update_status gauge
web_update_status {status}
# HELP web_check_last_time 最后一次检查时间戳
# TYPE web_check_last_time gauge
web_check_last_time {timestamp}
"""
    with open(f"{metrics_file}.tmp", "w", encoding="utf-8") as f:
        f.write(metrics)
    os.rename(f"{metrics_file}.tmp", metrics_file)

if __name__ == "__main__":
    try:
        status = check_web_update()
        write_metrics(status)
    except Exception as e:
        write_metrics(-1)  # 异常标记为-1
        print(f"网页检查异常: {e}")
```

#### 步骤 2：用 systemd 替代 crontab（定时+进程托管）
大佬不会用 crontab 定时，而是用 `systemd Service + Timer`（比 crontab 更稳定，能监控进程状态，挂了自动重启）。

##### 1. 签到脚本的 systemd 配置
新建 `/etc/systemd/system/signin.service`：
```ini
[Unit]
Description=签到脚本服务
After=network.target

[Service]
User=jw-yin
Type=oneshot  # 一次性执行（配合Timer定时）
WorkingDirectory=/home/jw-yin/scripts
ExecStart=/usr/bin/python3 /home/jw-yin/scripts/signin.py
Restart=no  # oneshot类型不用重启
# 日志重定向，便于排查
StandardOutput=journal+console
StandardError=journal+console
```

新建 `/etc/systemd/system/signin.timer`（每天 8 点执行）：
```ini
[Unit]
Description=每天8点执行签到脚本

[Timer]
OnCalendar=daily *-*-* 08:00:00
Persistent=true  # 错过执行时间（比如服务器关机），开机后补执行
AccuracySec=1min

[Install]
WantedBy=timers.target
```

##### 2. 网页监控脚本的 systemd 配置
新建 `/etc/systemd/system/web-check.service`：
```ini
[Unit]
Description=网页监控脚本服务
After=network.target

[Service]
User=jw-yin
Type=oneshot
WorkingDirectory=/home/jw-yin/scripts

新建 `/etc/systemd/system/web-check.timer`（每 6 小时执行）：

```

##### 3. 启动并启用 timer
```bash
# 重新加载配置
sudo systemctl daemon-reload

# 启动并开机自启定时任务
sudo systemctl enable --now signin.timer
sudo systemctl enable --now web-check.timer

# 查看定时任务状态
sudo systemctl list-timers
```

#### 步骤 3：配置 Node Exporter 采集自定义指标
Node Exporter 有个 `textfile_collector` 功能，能采集我们写入的指标文件，只需修改 Node Exporter 的启动命令：
```bash
# 先停止原有 Node Exporter
docker stop node_exporter && docker rm node_exporter

# 重新启动，挂载textfile目录
docker run -d \
  --name node_exporter \
  --net host \
  --pid host \
  -v /:/host:ro,rslave \
  -v /var/lib/node-exporter/textfile_collector:/var/lib/node-exporter/textfile_collector \
  --restart always \
  prom/node-exporter:latest \
  --path.rootfs=/host \
  --web.listen-address=127.0.0.1:9100 \
  --collector.textfile.directory=/var/lib/node-exporter/textfile_collector
```

此时访问 `http://127.0.0.1:9100/metrics`，能看到 `signin_status`、`web_update_status` 这些自定义指标，说明采集成功。

#### 步骤 4：Prometheus 配置告警规则
在 `alerts.yml` 里新增针对两个脚本的规则：
```yaml
- name: custom_scripts_rules
  rules:
    # 签到失败告警
    - alert: SigninFailed
      expr: signin_status == 0
      for: 1m
      labels:
        severity: critical
      annotations:
        summary: "签到脚本执行失败"
        description: "最后一次签到时间：{{ timestamp_to_time(signin_last_check_time) }}"

    # 网页有更新告警
    - alert: WebPageUpdated
      expr: web_update_status == 1
      for: 10s
      labels:
        severity: info
      annotations:
        summary: "监控网页有更新！"
        description: "最后检查时间：{{ timestamp_to_time(web_check_last_time) }}"

    # 脚本长时间未执行告警
    - alert: ScriptNotExecuted
      expr: time() - signin_last_check_time > 86400  # 超过24小时
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "签到脚本未执行"
        description: "已超过24小时未执行签到，检查timer是否正常"
```

重启 Prometheus 加载新规则：
```bash
docker restart prometheus
```

#### 步骤 5：Alertmanager 统一处理告警
不用改 Alertmanager 配置，所有告警都会自动通过 Alertmanager 发邮件——无论是服务器资源告警，还是脚本的签到失败/网页更新告警，都走同一个渠道，不用再为每个脚本写 ssmtp 逻辑。

### 大佬做法的核心优势（对你的价值）
1. **解耦**：核心脚本只做“签到/对比”，定时、监控、告警交给专业工具，改告警规则不用动脚本；
2. **稳定**：systemd 比 crontab 更可靠，能监控进程状态，脚本异常有日志可查；
3. **可扩展**：新增第三个脚本时，只需写指标文件+systemd配置+告警规则，不用复制一套 shell/ssmtp；
4. **安全**：敏感信息（邮箱授权码）存在 Alertmanager 的环境变量里，不硬编码在脚本中；
5. **可观测**：所有脚本的执行状态、结果都能在 Prometheus 查历史数据，出问题能快速追溯。

### 总结
大佬的核心思路不是“替换你的 Python 爬虫”，而是**把重复、通用的“定时、监控、告警”工作抽象出来，交给标准化工具**，让你的核心脚本只专注做“业务逻辑”。这既保留了你熟悉的爬虫写法，又解决了手工脚本零散、难维护、不安全的问题——这也是 DevSecOps “标准化替代手工、解耦替代内嵌”的核心思想。
